Problem Framing

The current target is precise and cohort-bound. It should not be described as broad all-active-user propensity.

Current MVP target: prior cart/purchase users

Business question

Among users with prior cart/purchase behavior, who is likely to buy in the next 30 days?

Prediction unit

client_id, one customer-level row.

Training row

One eligible client with historical features plus one future-window label.

Label

Binary indicator: has product_buy in the 30-day target window.

Feature window

Events before cutoff date 2022-11-09.

Target window

2022-11-09 through 2022-12-08.

Current cohort

Pre-cutoff add_to_cart OR product_buy users.

Limitation

Search/page expansion is future work; page visit is high-volume and deferred.

The current cohort is broader than cart-only because prior purchasers without cart history can also be eligible. Cart-only has 1,872,709 clients, while the current cohort has 2,149,796 clients, adding 277,087 clients beyond cart-only. Target-window purchase path validation also found many future buyers without pre-cutoff cart history, so the review recommendation is to keep the current MVP target but rename it as 30-day purchase prediction for prior cart/purchase users.

Feature And Label Logic

The supervised target is created from future purchase events after historical features are already separated by cutoff.

Association, not causality
Raw events

add_to_cart, remove_from_cart, product_buy, search_query, product_properties.

Before cutoff

Filter history to events before 2022-11-09 for feature construction.

User features

Counts, distinct counts, recency, ratios, category and price aggregates.

Target window

Future product_buy events define binary labels for eligible clients.

Training row

One client, one feature vector, one label.

Why counts?

Counts are baseline predictive signals for activity intensity. They do not prove that more events cause purchase.

Why recency?

Recent cart, purchase, or remove behavior can signal fresher intent than older history.

Why ratios?

Ratios summarize behavior relationships, such as purchase relative to cart activity, while handling zero denominators safely.

Search caveat

Search count has aggregate lift, but raw query meaning is noisy and intentionally not displayed.

Same-SKU path caveat

Only 3.579% of target purchase events had prior same-SKU add-to-cart, so same-item cart path is weak as a required assumption.

Future features

Sequence, category transition, session, and page-aware features are natural next iterations.

Modeling Baseline

Spark ML Logistic Regression gives an explainable MVP baseline with probability scores suitable for ranking and API serving.

36 numeric features

Model recipe

  • Spark ML Logistic Regression.
  • Median imputation for numeric input features.
  • VectorAssembler builds the feature vector.
  • Class weights enabled for sparse positives.
  • Random 80/20 train/test split with seed 42.

Metric interpretation

  • ROC-AUC measures ranking across thresholds.
  • PR-AUC is more useful than accuracy for imbalanced positives.
  • Top-K lift matches targeting workflows.
  • Probability score is more flexible than a hard label.
  • Calibration is not fully validated; use MVP score mainly for ranking.

A model could predict almost everyone as negative and appear accurate because positives are sparse. PR-AUC, recall, precision, and Top-K lift reveal whether positives are actually ranked well.

A probability-like score supports ranking, threshold review, campaign sizing, and later calibration. A hard label only answers one threshold choice.

FastAPI

Health, metadata, score lookup, manual prediction.

Endpoint Purpose Input Output Error behavior
GET /health Basic service readiness check. None. Status and service name. 200 when app is reachable.
GET /metadata Expose task, target window, model version, and serving mode. None. Task metadata and API mode. 200 when app is reachable.
GET /scores/{client_id} Lookup precomputed batch score. Client identifier from request path. Score, label, model version, scored timestamp. 404 if absent; 503 if score database unavailable.
POST /predict Manual feature-input prediction using exported Logistic Regression metadata. Feature dictionary. Score, label, decision, missing filled features, feature count. 422 for invalid feature values; 503 if model metadata unavailable.
Production alternatives would use Postgres, Redis, or an online feature/serving store. SQLite is intentionally a local MVP lookup layer, not a high-concurrency production store.

Limitations And Next Steps

The MVP demonstrates an end-to-end production-like path, but several choices remain review or future work.

Do not overclaim

Limitations

  • Current target is not broad all-active-user propensity.
  • page_visit is deferred due to cost-benefit and volume.
  • Random split baseline should later be improved with time-based backtesting.
  • Score calibration is not fully validated.
  • Count/recency features are simple baseline signals.
  • SQLite is MVP serving, not production high-concurrency storage.
  • Authentication and access control are not implemented.
  • Recommendation and sequence modeling are future extensions.

Next steps

  • Review target framing with mentor.
  • Adopt precise target language in mentor discussion.
  • Add time-based validation over multiple cutoffs.
  • Run threshold and cost analysis.
  • Broaden cohort with search/page only after dedicated EDA.
  • Explore sequence and category-aware features.
  • Move serving store to production-grade infrastructure if deploying.
